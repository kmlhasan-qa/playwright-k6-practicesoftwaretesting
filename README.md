# Practice Software Testing – Toolshop: UI, API & performance tests

Test automation for the public demo **[Practice Software Testing – Toolshop](https://practicesoftwaretesting.com)** (Sprint 5, [API v5](https://api.practicesoftwaretesting.com/api/documentation)). The workflow under test is **checkout**: browse → cart → sign in → billing address → payment → order (invoice).

| Deliverable | Location |
|---|---|
| UI + API automation (Playwright + TypeScript) | `tests/`, `pages/`, `fixtures/`, `helpers/` |
| Postman collection (+ last run result) | `postman/toolshop-api.postman_collection.json`, `postman/results/` |
| k6 performance script (+ smoke result) | `perf/checkout-load.js`, `perf/results/` |
| Test case catalogue, automated tests and why, automation explained, defect list and reports | `docs/test-cases-and-automation.docx` |
| Every run command on one page | [`RUN_COMMANDS.md`](RUN_COMMANDS.md) |

## Approach

My approach is to understand the product before deciding what needs to be automated. I don't jump straight into writing automation scripts because I believe effective test automation starts with understanding the product, its business logic, user journeys, and potential risks.

Here's how I approach the entire process:

**1. Product Understanding & Exploratory Testing**

Before starting automation, I first explore the product manually to understand its functionality, business flows, user interactions, and expected behavior.

In parallel, I use my Claude skill, `test-research`, to analyze the product and identify potential test scenarios across different testing dimensions:
- **Positive Testing:** Valid inputs and expected happy paths.
- **Negative Testing:** Invalid inputs and prohibited actions.
- **Boundary Testing:** Values at, below, and above defined limits.
- **Edge Case Testing:** Unusual but realistic situations involving timing, application state, and data.
- **Security Testing:** Potential vulnerabilities and unauthorized access.
- **Non-Functional Testing:** Performance, compatibility, accessibility, and other quality attributes.

The skill also helps identify potential defects and generates a structured testing report based on its analysis.

**2. Building Reusable Claude Skills**

If there isn't an existing Claude skill for a particular testing activity, I create one from scratch.

For example, if `test-research` doesn't exist yet, I first develop a prompt that instructs Claude to analyze the product, identify test scenarios, investigate potential defects, and generate a structured report. Once the prompt produces consistent and useful results, I turn it into a reusable Claude skill.

My intention is to make these skills reusable not only for myself but also for other team members and future projects.

**3. Comparing AI Findings with Manual Exploration**

After completing exploratory testing, I compare my manual findings against the report generated by `test-research`. This helps me:
- Identify scenarios that might have been overlooked during manual exploration.
- Validate AI-generated test scenarios against actual product behavior.
- Identify discrepancies between expected and actual results.
- Review potential defects and eliminate false positives.
- Assess overall test coverage and identify additional testing opportunities.

I treat Claude as a testing assistant rather than the final authority. All AI-generated findings are reviewed and validated before being accepted.

**4. Test Scenario Assessment & Automation Prioritization**

Once the exploratory testing and assessment are complete, I decide which scenarios should be automated. My focus is on selecting scenarios that provide the highest testing value while keeping the automation suite concise, reliable, and maintainable. I prioritize:
- Critical business flows.
- High-risk functionality.
- Frequently used user journeys.
- Regression-prone areas.
- Scenarios that provide meaningful coverage without unnecessary redundancy.

I also identify additional scenarios that could strengthen automation coverage while avoiding unnecessary complexity and unstable test cases.

**5. AI-Assisted Test Framework Development**

I have created two dedicated Claude skills to generate automation frameworks based on the architecture, coding standards, and best practices from my previous projects:
- `playwright-framework`: Generates a Playwright framework tailored to the target product.
- `k6-framework`: Generates a k6 performance testing framework tailored to the target product.

I provide these skills with the relevant project context and ask Claude to generate and execute the framework setup. The objective is to establish a consistent foundation with reusable components, configurations, utilities, and reporting capabilities, rather than building every new project framework from scratch.

**6. Test Automation Implementation & Review**

Once the framework is ready, I prepare a prioritized list of test cases that have been selected for automation. I then provide the test case list to Claude and ask it to implement the corresponding automation scripts using the newly generated framework.

After implementation, I review the generated automation to ensure:
- Test logic matches the intended scenarios.
- Assertions validate the correct expected behavior.
- Locators and synchronization strategies are reliable.
- Code follows the framework conventions.
- Unnecessary steps and redundant scenarios are removed.
- Tests remain concise, stable, and maintainable.

I then execute the automation suite, review the results, and make any necessary improvements.

**7. Automated Documentation & Execution Reporting**

To maintain documentation and traceability throughout the automation lifecycle, I created two additional Claude skills:
- `test-docs-sync`: Whenever a new automation script is created or an existing one is updated, this skill updates the automation documentation and records the changes in the report.
- `test-run-report`: Whenever an automation suite is executed, this skill updates the report with the latest execution results, including passed, failed, and other relevant findings.

This ensures that automation development and execution history are continuously documented without relying entirely on manual reporting.

## 1. Setup and execution

**Prerequisites:** Node.js 20+ (22 recommended), npm, [k6](https://k6.io/docs/get-started/installation/) for the performance tests, and [Docker Desktop](https://www.docker.com/products/docker-desktop/) for the k6 load runs (they run against a local copy of the Toolshop, never the public demo).

```bash
git clone https://github.com/kmlhasan-qa/playwright-k6-practicesoftwaretesting.git
cd playwright-k6-practicesoftwaretesting
npm ci
npx playwright install --with-deps chromium
cp .env.example .env        # optional – every value has a default
```

| Command | What it runs |
|---|---|
| `npm test` | all Playwright tests (API + UI) |
| `npm run test:api` | API project only (no browser) |
| `npm run test:ui` / `npm run test:headed` | UI project, headless / headed |
| `npm run test:e2e` | the successful end-to-end checkout (TC-UI-001) |
| `npm run test:defects` | executable defect reports only |
| `npm run test:postman` | Postman collection via newman |
| `npm run perf:smoke` | k6 smoke profile (safe for the public demo) |
| `API_URL=http://localhost:8091 npm run perf:load` | full k6 load model – against the **local Toolshop in Docker** (below), never the public demo |
| `API_URL=http://localhost:8091 npm run perf:normal` / `perf:ramp` / `perf:peak` / `perf:recovery` | one load phase on its own (normal 5/s, ramp 5→20/s, peak 20/s, recovery 5/s) – local Toolshop only |
| `npm run report` | open the last HTML report |

See [`RUN_COMMANDS.md`](RUN_COMMANDS.md) for the full list.

Environment variables (`.env` or shell): `BASE_URL`, `API_URL`, `HEADLESS`, `CUSTOMER_EMAIL`, `CUSTOMER_PASSWORD`. The k6 script takes `PROFILE`, `PHASE` (`all` \| `normal` \| `ramp_up` \| `peak` \| `recovery`), `API_URL` and `USER_POOL`.

**Local Toolshop (Docker) for load tests.** The k6 load profiles create thousands of orders, so they run against a local copy of the Toolshop started from the upstream project's Docker images (sprint 5, the same version as the public demo). Only the API, web server and database are started; the API is on `http://localhost:8091`.

```bash
git clone --depth 1 https://github.com/testsmith-io/practice-software-testing.git ~/toolshop-local && cd ~/toolshop-local
docker compose -f docker-compose.prod.yml up --pull missing -d laravel-api web mariadb
# before every load run: fresh data, then clear the API cache (otherwise the cached
# product list returns products the reset deleted, and every "add to cart" fails)
docker exec toolshop-laravel-api-1 php artisan migrate:fresh --seed --force
docker exec toolshop-laravel-api-1 php artisan cache:clear
```

Then run the load scripts with `API_URL=http://localhost:8091`, and stop the stack with `docker compose -f docker-compose.prod.yml down -v`. The shop and k6 share one machine, so these results show what that machine can handle, not the capacity of production.

**CI:** `.github/workflows/playwright.yml` runs the `api` and `ui` projects plus the Postman collection on every push, every PR and nightly, and uploads the reports. The k6 smoke run is manual only (workflow_dispatch), so the public demo never gets automatic load.

## 2. Framework structure

```

├── helpers/

│   ├── api/                   # project "api"
│   │   ├── auth.spec.ts       # register, login, password policy, age rule, breached passwords
│   │   ├── products.spec.ts   # list contract, detail, search, 404
│   │   ├── cart.spec.ts       # cart CRUD, quantity boundary values, price tampering

```

### The two high-value automated scenarios

| ID | Type | Scenario | Why it matters |
|---|---|---|---|
| **TC-UI-001** | Successful E2E | A new customer searches for a product → adds **2 units** → checks the cart total → signs in during checkout → completes the billing address through the postcode lookup → pays by credit card → confirms. The test then checks the invoice through the API: invoice number, total = 2 × unit price, the line item, the billing address and the payment method. | Checkout is the revenue path. The test proves the order was actually **persisted correctly**, not only that a "thank you" text appeared. |
| **TC-UI-002** | Negative / validation | An expired card (last month, the boundary) shows *"Expiration date must be in the future."* and disables **Check payment**. The test also checks that **no request** reaches `/payment/check` or `/invoices`, that the customer has no order, and that the cart is kept. | Payment validation is a high-risk area. Asserting on the network traffic as well as the UI catches a regression where the button stays enabled or the order is created anyway. |
| TC-UI-003 | Regression (`@defect`) | DEF-001: when the API rejects the order (422), the UI must tell the customer. Today it fails silently and still shows "Payment was successful". | An executable defect report: it turns green when the defect is fixed. |

### Design decisions

- **Two Playwright projects, one config.** The `api` project never starts a browser, so it is fast enough to run on every commit. The `ui` project uses Desktop Chrome.
- **Page Object Model + custom fixtures.** Specs read like the business flow, and each locator is defined once. Locators use the app's own `data-test` hooks (`testIdAttribute: 'data-test'`), which are more stable than CSS or text.
- **A fresh customer for every test.** The `customer` fixture registers a unique user through the API and logs in. Order history is then isolated from other runs and from other people using the shared demo, so tests can make exact assertions such as "this customer has exactly 1 invoice".
- **The API verifies what the UI did.** The E2E test reads the invoice back through the API, which avoids brittle text checks and catches persistence bugs.
- **Nothing hard-coded that the environment can change.** The demo database is reset periodically and product IDs are regenerated (seen during development). Tests look up a purchasable product at runtime. The billing city and state come from `GET /postcode-lookup`, because the API validates against it (the demo lookup uses a deterministic fake data generator, so real city names fail).
- **Waiting on application state, not on time.** The checkout pre-fills the saved address asynchronously, and the postcode lookup can be overwritten by it (see OBS-2). The page object waits for the pre-fill, then retries the lookup until the form holds exactly the lookup values. There are no fixed sleeps in the specs.
- **Request rewriting for a deterministic negative test.** TC-UI-003 uses `page.route` to put the customer's saved city into the real `POST /invoices` request. The real server returns its real 422, and the test observes how the UI reacts. Without this, the defect only reproduces when the timing is right.
- **Executable defects.** Tests tagged `@defect` assert the *correct* behaviour and are wrapped in `test.fail()`. CI stays green while a defect is open and turns red when it is fixed, which prompts removing the annotation.
- **Boundary values and data-driven tests** for cart quantity (0/1/99/100, decimal, text), password length (7/8) and card expiry (last month).
- **Diagnostics on failure only:** screenshot, video and trace, plus HTML and JSON reporters. Failing assertions include the request and response bodies.

## 4. Performance test (summary)

`perf/checkout-load.js` load-tests the shop's "booking" – placing an order. One k6 iteration is one realistic customer order: `POST /carts` → `POST /carts/{id}` (add 1 item) → `POST /invoices` (signed in, cash on delivery). A pool of 10 test customers is registered in `setup()`, and their tokens are refreshed before they expire.

### Workload model

The script uses an **open workload model** (k6 arrival-rate executors): new orders start at a fixed rate whether or not the system keeps up, just as real customers keep arriving when a shop slows down. A closed model (a fixed number of virtual users looping) would hide a slowdown, because slower responses would automatically lower the load. In the open model a slowdown shows up as higher latency, errors or dropped iterations. The rates apply to the booking call; each order adds about two supporting calls, so total HTTP traffic is about 3× the order rate.

| Phase | Executor | Rate | Duration (load profile) | What it answers |
|---|---|---|---|---|
| normal | constant-arrival-rate | 5 orders/s | 5 min | Is the shop within budget at expected traffic? |
| ramp_up | ramping-arrival-rate | 5 → 20/s | 5 min | At what rate does latency start to rise? |
| peak | constant-arrival-rate | 20/s | 5 min | Does it hold 4× normal traffic (a sale or campaign)? |
| recovery | constant-arrival-rate | 5/s | 3 min | Does it return to normal once the peak is over? |

`npm run perf:load` runs all four in sequence (about 18 minutes, about 12,000 orders); each phase can also run on its own (`perf:normal`, `perf:ramp`, `perf:peak`, `perf:recovery`). The **smoke** profile runs the same four phases at 1 order/s for 30 s each. Virtual users are sized with Little's law (VUs ≈ rate × iteration time), so k6 has enough of them to deliver the planned rate.

**Where each profile runs:** the smoke profile runs against the public demo. The full load profile and the single load phases run only against the local Toolshop in Docker (see section 1), so the shared demo never receives load.

### Metrics monitored

| Metric | Why |
|---|---|
| `order_success` (custom rate) and `checks` | Correctness first: an order counts only if the cart was created, the item added, the order created (201), an `INV-…` number issued **and** the invoice total equals the product price. A fast wrong answer is still a failure. |
| `orders_created` (custom counter) and `iterations` rate | Throughput actually achieved, compared with the planned rate |
| `http_req_duration` of `POST /invoices`, **tagged per phase** | Booking latency (median, p95, p99, max) for each phase separately, instead of one blended average |
| `http_req_duration{flow:cart}` | Latency of the supporting cart calls |
| `order_flow_duration` (custom trend) | The whole three-step order as the customer experiences it |
| `http_req_failed`, overall and for `POST /invoices` | Error rate of the booking call and of all traffic |
| `dropped_iterations`, `vus` / `vus_max` | Whether k6 really delivered the planned load. Without this, a "fast" result could just mean the load was never applied. |

On an environment with server access I would also watch the server side during the run: CPU and memory of the API and database containers, PHP-FPM workers and queue, database connections and slow queries, and the application error log. The k6 numbers show *that* the shop slowed down; these show *why*.

### How the thresholds were chosen

| Threshold | Limit | Reasoning |
|---|---|---|
| Order success, checks | > 99% | Correctness before speed; 1% is the most a shop would tolerate for failed orders |
| Booking errors (`POST /invoices`) | < 1% | A common target for a transactional endpoint |
| All HTTP errors | < 5%, aborts the run after 30 s | A safety valve: stop loading a system that is clearly broken |
| Booking p95, normal and recovery | < 1000 ms (p99 < 2000 ms at normal) | Measured smoke baseline on the public demo was 0.34–0.53 s p95 across the 7–8 Nov 2026 runs, so about 2× headroom |
| Booking p95, ramp and peak | < 1500 ms (p99 < 3000 ms at peak) | Some slowdown under 4× load is acceptable, at most +50% over the normal budget |
| Cart calls p95 | < 800 ms | Simpler calls, so a tighter budget |
| Whole order p95 | < 3000 ms | What the customer actually waits for (3 calls) |
| Dropped iterations | < 10 | Proves the planned load was delivered |

The latency limits come from measured baselines plus headroom, combined with common web-performance budgets. There is no business SLA for this demo; with a real shop, the limits would come from the business (conversion data, an agreed SLA) and from production monitoring.

### Limitations and risks

- **Not production capacity.** Load runs use a local Docker copy on one laptop. k6 and the shop share its CPU, and there is no internet latency, so booking p95 is about 15–22 ms there against 340–440 ms on the public demo. The local results confirm the script and the model, and show the laptop easily handles 5–20 orders/s. They don't say what production can handle, and 20 orders/s never pushed the local shop near its limit.
- **The public demo only gets smoke runs.** It is shared with other people, and its rate limits and hardware are unknown, so it can't be load-tested responsibly. Its smoke numbers also vary between runs and include internet latency.
- **The rates are assumptions.** 5 and 20 orders/s are not derived from real traffic analytics. With a real shop they would come from peak-hour order data.
- **Narrow traffic mix.** Every iteration is the same order: one item, cash on delivery, the first purchasable product. Browsing, search, other payment methods, larger carts and guest checkout are not part of the load, so database hot spots (one product row) and cache behaviour may not match reality.
- **Short runs.** Phases last 5 minutes. Memory leaks, connection-pool exhaustion or token-refresh problems over hours need a soak test (normal rate for 1–2 h), which hasn't been run.
- **Test data.** The local database is reset before each run, so results don't reflect a large, aged database. The API cache must be cleared after each reset, or every order fails in setup. A small pool of 10 customers places all orders, which is unrealistic for per-user locking or rate limits.
- **No server-side metrics** in the current runs, so a slowdown could be seen but not explained.

Run results for every run kind are in `docs/test-cases-and-automation.docx` §6.5; the document's §3.4 has the same model in short form.

## 5. What I would improve with more time

- **Own environment in CI.** The k6 load runs already use a local Toolshop in Docker. The next step is to start the same stack in CI and point every suite at it, so CI no longer depends on, or pollutes, the shared demo and the database is reset per run.
- **More checkout coverage:** guest checkout (`/invoices/guest`), and changing the quantity or removing a line in the cart through the UI. (The other payment methods are covered at API level by TC-API-037.)
- **Contract tests** generated from the OpenAPI spec (e.g. `ajv` against `/docs?api-docs.json`) instead of hand-written `toMatchObject`.
- **Session reuse** with `storageState` for UI tests that don't need to exercise login.
- **Cross-browser and mobile** projects, accessibility checks (`@axe-core/playwright`) and visual snapshots of the checkout steps.
- **Performance:** a per-phase HTML report (k6 web dashboard), server-side metrics (APM, DB) correlated with the k6 run, and a soak test (normal rate for 1–2 h) to find leaks and token-refresh problems.
- **Defect workflow:** link `@defect` tests to tracker IDs and post the pass/fail summary to Slack/Teams from the JSON report.
